# Contributing to VoxFrontier

Thanks for your interest in improving VoxFrontier! This project aims to be a
reference-quality implementation of efficiency + causal analytics, so the
quality bar is intentionally explicit.

By participating you agree to abide by the
[Code of Conduct](CODE_OF_CONDUCT.md).

## Development setup

```bash
git clone https://github.com/GOOD-123-CPU/voxFrontier.git
cd voxFrontier
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -e ".[dev]"
pre-commit install    # formatting + local privacy guard on every commit
pytest                # must be green before any PR
```

Optional extras:

```bash
pip install ".[pulp]"   # exact MILP DEA backend
pip install ".[shap]"   # SHAP explainability plots
```

Convenience shortcuts live in the `Makefile` (`make lint`, `make test`,
`make run-all`, `make audit`). A one-click dev environment is available via
the included dev container.

## Ground rules

1. **Privacy is non-negotiable.** Never commit real streamer names, room
   IDs, raw audio, or any licensed dataset. The repo ships *only* synthetic
   data generated by `voxfrontier.data.synth`. CI runs a privacy audit over
   the working tree **and the entire git history** — keep it green.
2. **Every estimator needs a test with a known answer.** Recovery tests
   (planted effects, known DEA solutions, conformal coverage) are the
   project's core asset — extend them whenever you touch math.
3. **No hard-coded results.** Anything that looks like a cached statistic
   must be computed from data. The Shapley anti-caching test is the
   precedent.
4. **Reproducibility**: new outputs must be registered in the manifest and
   covered by the CLI end-to-end test.
5. **Style**: `ruff check src tests` must pass; keep the public API typed
   and docstrings honest (English preferred, 中文 welcome in discussions).

## Pull requests

- One logical change per PR; include tests and a CHANGELOG entry.
- CI must be green (lint + privacy audit + tests across OSes + CodeQL).
- Explain *why*, not just *what*, in the PR description.

## Reporting issues

Include: OS/Python, minimal reproduction (config + command), and the
`output/manifest.json` of the failing run if you have one.
Security or privacy issues go through the private channel in
[`SECURITY.md`](SECURITY.md) — never a public issue.
